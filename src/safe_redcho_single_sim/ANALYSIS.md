# Existing simulation analysis and baseline decision

The source snapshot is recorded in `provenance/original_source_sha256.json`. The latest scenario is `safe_redcho_distributed/reactive_scenario.py`, selected by its `scenario.py`. The recorded `results/redcho_pose_full` run uses this position/height formation version, six aircraft, a 45 s logged mission and a fault on cf2 at 17 s. Older STEP2/3/4 README files describe earlier replay stages; they are not the current Gazebo architecture. Some historical checks import APIs no longer present in current formation code.

The current closed-loop path is `control_agent.py` -> `local_controller.py` -> `formation_control.py`, coordinated by `gazebo_mission.py`. Every agent has local battery, SVF, velocity REDCHO and position REDCHO computations. `LocalObserver` also runs a separate Levant-based velocity REDCHO as an ablation. Thus operational control uses velocity/position banks, while the total implementation includes that additional comparison bank. Simply hiding a plot would not produce a single-bank baseline.

`pose_redcho.py` already integrates the local filtered XY velocity and produces position, velocity and acceleration estimates. Its vertical input is an analytic takeoff towards six distinct height proposals averaging 0.8 m. Only zeroth-order displacement estimates are exchanged with two ring peers. This is the reusable architecture for the requested baseline.

The new package instantiates one `PoseREDCHO` object per aircraft. The local SVF remains a reference filter, not a consensus bank. Its integrated XY displacement and analytic height feed that bank. All p/v/a tracking outputs come from the bank. There is no independent velocity REDCHO, no Levant REDCHO, and no centralized average used for control. Centralized averages appear only in telemetry as independent error oracles.

The battery model, initial charges, cf2 fault, reference heading, filtered-input regularity, position REDCHO parameters, feedback gains, QP, geometric controller, motor allocation, physical masses/inertias/drag and scenario geometry are preserved. Only the reference-bank architecture changes. Consequently trajectories, power consumption and terminal battery histories need not be numerically identical to the dual-bank experiment.

The native Gazebo backend `safe_redcho_lockstep` applies six four-motor force commands for ten 1 ms physics steps, then returns synchronized poses/twists and actual applied force/limit readbacks. The coordinator advances only after six same-cycle local results. This remains the plant: the new Gazebo driver does not integrate a Python substitute or teleport aircraft. Its separate offline runner is clearly labelled a numerical SE(3) screening model.

All original packages are reused read-only or left untouched. Physical worlds are copied byte-for-byte into this package, still referencing shared mesh assets and the original native plugin. The backend's `/safe_redcho/step` and `/cfN/state` endpoints are fixed in that plugin. Use an exclusive ROS domain and Gazebo partition per experiment. The new control/ring/results channels are isolated under `/safe_redcho_single_sim`; the recommended ROS domain is 47 instead of the older simulation's 42 or hardware's 43.

Testing also exposed that shutting down the Gazebo Ruby CLI wrapper could leave its native backend child alive. The new package adds an owned-process supervisor and descendant reaping; it does not alter the shared C++ plugin. Test cleanup is checked separately from controller/physics PASS results.

CSV/NPZ telemetry, saved scientific plots, Gazebo/RViz views, ground hold, takeoff/hover gate, forward motion, both obstacle encounters, battery fault and final formation-recovery checks are retained. Velocity-bank/Levant-ablation plots are replaced with truthful single-bank position/velocity/acceleration reconstruction plots. Missing banks are never represented by invented arrays or zeros. The original scenario ends with the world paused in flight; this package retains that behavior rather than inventing a landing phase.
